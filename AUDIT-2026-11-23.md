# Audit — 23 November 2026

Scope: the deployed Patient Directory (`clinic-ochre-seven.vercel.app`), its persistence layer, its
backup mechanism, and the October–November data-loss incident. Written after the fact, from evidence
gathered on the affected machine; no patient records were modified during the audit.

## 1. Cause of the loss

| Date | Change | Effect |
|---|---|---|
| before 19 Oct 2026 | patients written to `localStorage['patients']` | durable on that browser |
| 19 Oct 2026 22:46 UTC | `60c7f4a` "Connect patient directory to Supabase database" | **every `localStorage` write removed**; saves became inserts to `oqarvapuiiqfjemqubh.supabase.co` |
| 19 Oct → 19 Nov | inserts fail at DNS; the handler only printed `⚠ insert failed` | nothing persisted locally or remotely |
| 19 Nov 2026 06:11 UTC | offline-first rewrite deployed | 31 pre-existing rows recovered from the untouched legacy key |

`oqarvapuiiqfjemqubh.supabase.co` does not resolve today, and passive DNS (mnemonic) holds **zero**
historical records for it, so the host never served a query. The records typed between 19 Oct and
19 Nov were never stored anywhere: not in localStorage, not in IndexedDB, not on a server, not in the
backup endpoint (which was never configured). The 31 that came back are the register as it stood
before the broken version.

## 3. What survives what

| Event | Records survive |
|---|---|
| refresh, browser restart, redeploy, offline | yes |
| another browser, private window | no |
| "clear browsing data" | no |
| device lost or replaced | only if a backup file exists |

## 4. Risks

| Risk | Severity | Status |
|---|---|---|
| single copy on one device, no off-device backup | high | needs `GITHUB_TOKEN` + `BACKUP_REPO` in Vercel |
| browser eviction under disk pressure | medium | page now requests persistent storage; browsers may still decline (`persisted()` returned `false` in a fresh test profile) |
| 31 real patients embedded in the public page and repo | high (privacy) | unresolved, owner decision |
| silent storage failure | medium | handled: red pill + banner + backup prompt |
| duplicate records after restores | low | handled: merge on uid → registration → phone |
| accidental delete | medium | handled: tombstones, undo, version history, restore |

## 5. Backup behaviour

- **Manual:** header **Backup** → **Download backup now**. The file is parsed back and its record
  count checked before the download starts; the toast only claims success after that check.
- **Automatic on-device versions:** every add/edit/delete writes a version into IndexedDB `history`,
  each downloadable and restorable from the Backups panel.
- **Owner-side snapshots:** `api/backup.js` is present but inactive (`configured:false`). Two Vercel
  environment variables activate it: `GITHUB_TOKEN` (contents read/write on one private repo) and
  `BACKUP_REPO` (`owner/repo`). Once active the header pill reads `backup: saved <time>` and a fresh
  device merges the newest snapshot on load.

## 6. Verification run on the live build

Executed in a real browser against `localhost` serving this exact file, then against the deployment:

1. 31 rows on load; green pill `✓ saved on this device · 31 records`.
2. Added a patient → 32 in the UI, in `localStorage`, in the legacy mirror and in IndexedDB.
3. Reloaded → still 32 in both stores.
4. **Backup** → `Backup verified: 32 records downloaded.` and the panel recorded the download time.
5. Deleted the patient → 31 rows and a tombstone for its uid.
6. Imported the 32-row backup file → back to 32 with the tombstone cleared. Nothing was overwritten.
7. Live deployment → 31 rows, `backup: server not set up`, persistent-storage request present.

Not covered by this run: the restore-from-history button was exercised in the earlier round, and the
persistent-storage outcome itself (the browser may decline the request).

## 7. Still open

1. Off-device backup stays manual until the two Vercel variables exist.
2. The public built-in registry exposes real names and phone numbers; removing it needs a decision
   and a backup file first.
3. Records entered between 19 Oct and 19 Nov are unrecoverable from every store checked.
